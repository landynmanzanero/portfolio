Overview

CommBank’s developer portal had one problem: it dropped developers at the door with nothing but a link to documentation. No onboarding, no direction, no sense of where to start. We partnered with the Payments team to figure out what a genuinely developer-first portal could look like.

How might corporate payments learn from developer-first platforms like Twilio, Stripe, and Snowflake?

My Role

As the only team member with an engineering background, I took on a lead role in translating a technically complex domain for the team. The team came from different backgrounds, so the first sprint was about building shared context before we could design for it.

I led Sprint 1 (Research) end-to-end: defining our research approach, recruiting participants, and conducting the majority of our interviews with senior software engineers. After an independent lo-fi round, the team aligned on a direction and collaborated to develop it into the high-fidelity prototype.

Research

This is the sprint I led.

We benchmarked five platforms and talked to 10 engineers to understand what great developer experience actually looks like, and more importantly, what keeps getting in the way of it.

Competitive Analysis

Shared strengths
  • Developer-first information architecture
  • Self-service access, no sales call required
  • Interactive sandbox environments
  • Personalized onboarding
Shared weaknesses
  • Inflexible or opaque pricing
  • High technical ceilings that gatekeep less experienced developers
  • Sales-gated onboarding creates friction before developers see value

Synthesis

Affinity Mapping

We mapped everything we heard into clusters and let the patterns speak.

Two Personas

We built two personas grounded directly in our interview data, representing the two most common developer profiles we encountered.

Needs docs that reflect today, not six months ago. Outdated documentation doesn’t just slow her down, it breaks her trust in the whole platform.

Needs to decide without talking to sales. If onboarding is gated, he’s already moved on.

Every design decision ran through these two lenses: what does Eli need at onboarding, and what would Dara actually click on.

Journey Maps

Mapping both journeys across seven stages made one thing clear: trust didn’t break at implementation. It broke earlier, at onboarding, before developers had even seen what the platform could do.

Six Key Insights

Self-Sufficient Documentation Developers want to integrate without contacting support. Documentation is the primary onboarding tool.
External Integration Experience Poor documentation, unclear ownership, and compatibility uncertainty make external APIs hard to trust.
Smooth Hand-Off Consistent naming conventions and readable patterns reduce confusion in multi-team API ecosystems.
Use Case Flexibility Rigid APIs that don’t adapt to developer workflows limit adoption and innovation.
Security First Trust is built through sandbox credentials, clear compliance guidance, and transparent authentication requirements.
Building User Dependency Reliability signals, uptime, rate limits, changelogs, determine long-term trust. APIs that go quiet get abandoned.

Ideation

Using Crazy 8s and a 2x2 impact/effort matrix, we generated and prioritized eight feature concepts down to four.

Crazy 8s: eight feature concepts organized by developer pain point

High Priority Features

Personalized Onboarding

An adaptive quiz that tailors the portal experience to each developer’s role, experience level, and goals.

Learning Hub

A unified resource center with tutorials, guides, and documentation organized around real use cases.

Interactive Testing

A sandboxed environment for testing real API requests without external setup.

Notifications

A centralized feed for API changes, updates, and warnings so teams can plan safely.

User Flow

The user flow became the structural backbone of the prototype:

Homepage → Onboarding Quiz (4 steps) → Personalized APIs Page →
Specific API → [Introduction · Use Cases · Learning Hub · Documentation · Interactive Testing · Recent Updates]

Prototype

Screen 1: Personalized Onboarding

Four questions, enough to personalize without losing people to drop-off. Skip is always visible because developers told us they distrust any friction before they’ve seen value. The progress bar is a small thing that does a lot: it signals commitment, not a trap.

Screen 2: APIs Page

Recommendations surface first based on quiz answers, but nothing gets hidden. We heard this clearly from senior engineers: restrict visibility and you lose trust immediately. Personalization without paternalism.

Screen 3: Learning Hub

One hub, two modes. Beginners want walkthroughs, senior engineers want reference docs. The tab structure came directly from what people described in interviews, different formats for different stages.

Screen 4: API Playground

The blank sandbox problem is real: developers open a playground with no obvious starting point and immediately feel lost. Scoping by goal before you start (Process Payments, Retrieve Data, Authentication) removes that moment of confusion.

Screen 5: Documentation

Three columns mirroring Stripe and Twilio. The anchor links came from a specific complaint we heard: having to scroll through pages of documentation just to find one parameter. Jump-to links solve that.

Design Outcomes

Clearer Onboarding

A four-step quiz routes developers to relevant APIs, tutorials, and entry points immediately on landing, reducing the “what do I do next?” ambiguity.

Stronger Trust Signals

Security requirements, uptime metrics, and version changelogs surfaced earlier in the developer journey, addressing the trust breakdown at Onboarding and Research stages.

Faster Time-to-First-Success

The API Playground eliminates external setup, so developers make their first real API call from within the portal, directly reducing time-to-value.

Self-Sufficient Discovery

The Learning Hub, Use Cases, and FAQs sections consolidate scattered resources into one navigable center, reducing the back-and-forth developers described as their biggest frustration.

Reflections

What I’d Do Differently

We didn’t run usability testing on the final prototype before presenting. The research was genuinely strong, but there’s a difference between validating assumptions and watching someone actually use what you built. I’d want at least two rounds of testing with developers similar to Dara and Eli before any handoff.

What This Project Taught Me

Research is the groundwork everything gets built on. That sounds obvious until you’re sitting across from a Staff Engineer at Google who tells you exactly why they abandoned the last API they tried to adopt, and you realize that without that conversation, you would have designed the wrong thing entirely. The interviews made this project.
